Virtual Machine as a Service (VMaaS) offers you the ability to provision, update and unprovision virtual machines in minutes in a fully automated manner. The service is integrated into Cloud Foundry marketplace and will run the virtual machines in Openstack.

Services
Virtual Machine as a Service provides three different services

Virtual Machine Jump host

Virtual Machine (Linux)

Virtual Machine (Windows)

Operating Systems
Virtual machines are available with the following operating systems

Red Hat Linux 8 (RHEL)

Red Hat Linux 9 (RHEL)

Ubuntu 22

Ubuntu 24

Windows Server 2019 (W2K19) (deprecated)

Windows Server 2022 (W2K22)

Windows Server 2025 (W2K25)


With great power comes great responsibility.

— Spider-Man

Unmanaged Service
Virtual Machine as a Service is an unmanaged service.

What does this mean?
Unmanaged means that VMaaS provides virtual machines that are based on the hardening guidelines from EISA. When the provisioning is done, the customer gets root/administrator access to the virtual machine. The customer is the only one that has access to the virtual machine and therefore needs to take care of the EISA regulations to be compliant. We provide infrastructure (e.g. patch management systems) to support the customer, but the customer is responsible for doing so.

What is included?
The virtual machine is created on a current hardened operating system image.

The virtual machine is configured to be connected to the network, so that it has the promised connectivity.

The virtual machine is activated and has a valid license.

The virtual machine is connected to the patch management system, so that it can receive patches.

From service provider perspective we ensure that the virtual machine can run on the underlying infrastructure (Openstack).

What is not included?
The virtual machine will not be actively patched.

The audit logs of the virtual machine will not be automatically forwarded.

The virtual machine does not have any malware solution or endpoint protection installed.

The virtual machine has no automatic backups created, not any automation to restore backups.

There is no central monitoring of the virtual machines. As customer, you need to monitor the relevant data (e.g. CPU, RAM, disk storage, …​) of your VMs to make sure they operate properly.

Network Topology
All virtual machines provisioned by VMaaS are placed in the Openstack tenant of VMaaS. Within the VMaaS Openstack tenant the virtual machines will be micro segmented in dedicated networks for each customer (Cloud Project). All the virtual machines that will be provisioned within one Cloud Project will be placed in the same network. Each network has a /26 subnet, which means that it has 64 IP addresses. As there are a few required for default gateway, broadcast and DHCP at the end 58 IP addresses are available for customers. That means that a customer can provision up to 58 VMaaS virtual machines in one Cloud Project. Communication between virtual machines within one customer network is possible on all ports for TCP, UDP and ICMP, while communication between different networks, meaning different customers, is not enabled by default.

Difference between a Jump Host and standard Virtual Machine
VMaaS provides virtual machines as a platform service on the Bosch Private Cloud, which means that the virtual machines are provisioned in Openstack. Within the Openstack tenant these virtual machines get an internal IP address (192.168.0.0/16), which is accessible only from within the Openstack tenant. To be able to connect to a virtual machine from the outside, e.g. from the Bosch Corporate Network, it is required to have an external IP address (also known as floating IP address).

Now, the difference between a Jump Host and a standard Virtual Machine are two things:

The Jump Host has assigned an external IP address by default

The Jump Host has a specific security group on Openstack level assigned, that allows to access the Jump Host from anywhere. For a Linux Jump Host this is for port TCP/22 (SSH) and for Windows Jump Hosts this is port TCP/3389 (RDP).

By default, a standard Virtual Machine has no such external IP address assigned, which means you can not access it from the outside and also this virtual machine can not connect to other services in the Bosch Private Cloud.

Also, so-called ingress on the virtual machine is only enabled for virtual machine located in the same network (Cloud Project). It is possible to assign an external IP address also to a standard virtual machine and ingress you can manage in self-service via REST API.

Obligations of service recipient

Terminology
Maintenance
Maintenance describes planned changes to the service to patch, update or upgrade systems that are required to provide and operate the service. Planned changes will be communicated upfront via SPoI, especially when a downtime is involved with the changes.

Downtime
Downtime depicts a situation where either the service instance or the management functionality are not available. A downtime can be caused by planned changes that cause a downtime for the customer or incidents that have impact to the availability of the service instance or management functionality.

Incident
An incident is by definition unplanned and depicts a situation where the service does not normally operate. This may have impact to the availability of the service instance or the management functionality.

When to use what?
While an Openstack tenant provide you with more flexibility and features, it also comes with additional responsibilities.

When to use VMaaS?
When you just need a standard Virtual Machine or Jump Host and you have no special requirements on operating system or hardware specification VMaaS is the easier choice.

Especially if you are not familiar with Openstack and managing the Infrastructure on your own, it means a lot of additional resources you need to manage in an Openstack tenant:

routers

networks

subnets

ports

floating ips

security groups

volumes

servers

When to use an Openstack tenant?
If you have special requirements on operating system or hardware specification, you use additional resources in Openstack, e.g. Load Balancers or automate the Infrastructure rollout, then an Openstack tenant is the better choice for you.

NOTE

In general, if you have doubts or questions on what to use, please use one of the Support channels to get help.

There you also find the service parameters. At the moment we have the following optional service parameters:

external-ip - boolean

additional-storage - number between 0 and 8192 GB

availability-zone - enum with values none, nova, nova-az2 and nova-az3

initial-password - password for initial credential created for virtual machine

Linux only Service Parameters
authorized-keys - list of public ssh keys

automatic-patching - enable automatic patching on the VMaaS Linux VM

web-console - enable the Red Hat Enterprise Linux Web Console on the VMaaS Linux VM

Windows only Service Parameters
automatic-patching - JSON object that contains the three properties enabled, scheduled-day and scheduled-hour

enabled - enable automatic patching via Windows Update Server Service (WSUS)

scheduled-day - 0-7: 0 for every day, 1 for Sunday, and so on

scheduled-hour - 0-23: 24-hour format

iis - enable Internet Information Server (IIS) on the VMaaS Windows VM

boot-disk- number between 0 and 8192 GB
External IP
The checkbox external-ip allows you to assign an external IP also known as floating IP to your Windows or Linux virtual machine. The default for external-ip is false.

Floating IP Pool
The floating-ip-pool service option allows you to provide the name of a Floating IP Pool service instance located in the same space where the virtual machine is placed. When specified this will override the external-ip service option, meaning that in case of providing such a floating IP pool automatically a floating IP from that floating IP pool is assigned to the virtual machine.

The floating-ip-pool service option will be validated to ensure that a service instance with the specified name exists and that the service instance is of the required type. Additionally, the state of the service instance is validated so that a floating IP from that floating IP pool can be taken.

For more details on Floating IP Pools, please refer to Pool of floating IPs for your VMs.

Additional Storage
With additional storage you can provision additional storage on top of the storage that comes with the service plan on your workload virtual machine. All the additional storage will be charged extra. It is possible to update the additional storage when updating the service instance. Additional storage that is added at provisioning will be automatically mounted into the filesystem.

Windows virtual machines
For Windows virtual machines the storage is added to the D drive.

Linux virtual machines
For Linux virtual machines the storage will be mounted at /pkg.


NOTE

It is not possible to shrink the storage as this could lead to data loss.

Availability Zone
You may choose the availability zone (AZ) which your VM is going to be provisioned in. If you do not want to specify a value, you can still leave that field blank. In this case, we will choose the best availability zone based on the current system’s load. When you choose an availability zone it can not be changed afterward! The table below shows the availability zones that are available per environment and foundation, as well as in which of them you can set this value as input when creating VMs.

TIP

This feature is intended especially for customers that want to deploy multiple virtual machines in different availability zones to increase the overall availability, when load balancing between the virtual machines in the different availability zones.

For more information about availability zones refer to Availability Zone Concept.

Authorized Keys
With authorized key you can provide a list of public ssh keys that are added to the list of authorized keys for the created user, so that you can access your Linux virtual machine not just with username and password, but also with your ssh key.

This will improve your ability to automate your setup by using e.g. Terraform, as you are no longer required to retrieve the generated initial password for the first login on your virtual machine.

Automatic Patching
VMaaS RHEL Linux VMs
When enabling the automatic patching checkbox the necessary package dnf-automatic is installed at provisioning, apply patches is enabled and the necessary service dnf-automatic-install.timer is enabled and started. For more details please refer to Patch Management on a RHEL Linux VMaaS VM.

NOTE

Enabling automatic patching will not automatically reboot the virtual machine. For patches that require a root it is required that you check and reboot manually.

VMaaS Ubuntu Linux VMs
When enabling the automatic patching checkbox the necessary service unattended-upgrades is enabled and started. For more details please refer to  Patch Management on an Ubuntu Linux VMaaS VM.

NOTE

Enabling automatic patching will not automatically reboot the virtual machine. For patches that require a root it is required that you check and reboot manually.

VMaaS Windows VMs
When enabling automatic patching on Windows you need to specify when Windows Update Server Service (WSUS) will be executed. There you need to specify the day (0 for every day; 1-7 for all the week days starting with Sunday) and the hour (0-23 in 24-hour format). In case Windows patches are applied that require a reboot the reboot will be automatically triggered, which will lead to a short downtime of the Windows server during the reboot.

Web Console
The RHEL web console is a Red Hat Enterprise Linux web-based interface designed for managing and monitoring your local system.

When enabling the web console checkbox the necessary package cockpit is installed at the provisioning, the service cockpit.socket is enabled and a firewall rule for port 9090 is added. As result the web ui is accessible at https://<internal-dns>:9090. The web ui is using a self-signed certificate, and you can log in with the credentials also used for login on the virtual machine.

For more information on the Web Console read Managing systems using the RHEL 8 web console.






NOTE

By default, no ingress security group rule will be created to access the web ui from external. This is for two reasons, the exposure would require an external IP (also known as floating IP), which is not added to all the VMaaS VMs by default and exposing the web ui would be an additional attack vector. Therefore, we recommend to use e.g. Windows Jump Host, which is located in the same network from which you can access the Web Console.
Also, it is to mention that access on the web ui is limited when using the vmaas user instead of the root user. Therefore, you will see an information at the top Limited access and not all the functionality is available.

Internet Information Server (IIS)
When enabling the Internet Information Server (IIS) on a VMaaS Windows VM the Internet Information Server (IIS) feature on the Windows Server is enabled. In addition, on the host firewall ingress for ports 80 (HTTP) and 443 (HTTPS) will be enabled and an Openstack Security Group vmaas-iis will be attached to the VM, that also opens up ingress on ports 80 (HTTP) and 443 (HTTPS).

When you check the external-ip service option in addition, the Internet Information Server (IIS) will be automatically be reachable from the Bosch Corporate Network (BCN) via HTTP.

Just check out http://<external-dns>/iisstart.htm

Once you have configured a server certificate and configured the binding for HTTPS this also works with HTTPS.

Provision a Virtual Machine via CLI
To get a list of available services and service plans you can query the marketplace.



cf marketplace 
There you find the necessary information to create a service instance.



cf create-service <service> <service-plan> <name> 
for example:



cf create-service vmaas-linux "Medium (RHEL 8)" linux-medium-vm 
You can also provision a virtual machine with an external IP, additional storage, availability zone, authorized keys and all the other service parameters, by providing additional parameters, such as external-ip, additional-storage, availability-zone (refer to the table above for the environments and foundations that support this feature), authorized-keys and so on.

Windows:



cf create-service <service> <service-plan> <name> -c "{\"external-ip\":<boolean>,\"additional-storage\":<number>,\"availability-zone\":\"<string>\",\"authorized-keys\":[\"<public-ssh-key-1>\",\"<public-ssh-key-2>\"]}" 
Linux:


cf create-service <service> <service-plan> <name> -c '{"external-ip":<boolean>,"additional-storage":<number>,"availability-zone":"<string>","authorized-keys":["<public-ssh-key-1>","<public-ssh-key-2>"]}' 
for example


cf create-service vmaas-linux "Medium (RHEL 8)" linux-medium-vm -c "{\"external-ip\":true,\"additional-storage\":400,\"availability-zone\":\"nova-az2\"}"
NOTE

The service instance will be created in the organization and space the CLI is targeted at. 

To switch the organization/space use



cf target -o <organization> -s <space> 

Provision a Virtual Machine via Terraform
First, be sure that you read and configure your environment following Initial Terraform preparation for use with VMaaS

For this example, use below parameters as input:

Deploying a Linux Instance.

Organization=<Cloud Foundry Organization Name>

Space=<Cloud Foundry Space Name>

Service Name=vmaas-linux

Service Plan=Medium (RHEL 8)

Instance Display Name=Terraform Linux Instance DEMO

External Ip set to true

change file vmaas/demonstration.tf as below:



data "cloudfoundry_org" "org" {
    name = "bhc-vmaas"
}

data "cloudfoundry_space" "space" {
    name = "terraform_managed"
    org = data.cloudfoundry_org.org.id
}

data "cloudfoundry_service" "svc" {
    name = "vmaas-linux"
}

resource "cloudfoundry_service_instance" "svc_instance" {
    name = "Terraform Linux Instance DEMO"
    space = data.cloudfoundry_space.space.id
    service_plan = data.cloudfoundry_service.svc.service_plans["Medium (RHEL 8)"]
    json_params = "{ \"external-ip\": true, \"authorized-key\": [\"ssh-rsa ...\"] }"
} 
run plan phase



$ terraform plan -var-file environments/demonstration/variables.tfvars -out plan.out 






run apply phase



terraform apply plan.out 



For this example, use below parameters as input:

Deploying a Windows Instance.

Organization=<Cloud Foundry Organization Name>

Space=<Cloud Foundry Space Name>

Service Name=vmaas-windows

Service Plan=Micro (W2K19)

Instance Display Name=Terraform Linux Instance DEMO

External Ip set to true

ADD to file vmaas/demonstration.tf as below:



data "cloudfoundry_service" "svc2" {
    name = "vmaas-windows"
}

resource "cloudfoundry_service_instance" "svc_instance2" {
    name = "Terraform Windows Instance DEMO"
    space = data.cloudfoundry_space.space.id
    service_plan = data.cloudfoundry_service.svc2.service_plans["Micro (W2K19)"]
    json_params = "{ \"external-ip\": true }"
} 

run plan phase



$ terraform plan -var-file environments/demonstration/variables.tfvars -out plan.out 





run apply phase



$ terraform apply plan.out

When the hardware specification that you have selected for your virtual machine does not fit anymore, and you want to change it, you can do so in self-service. In addition to updating the hardware specification of your Linux or Windows virtual machine, you can also assign or remove an external IP to your virtual machine using update. This is also possible without changing the hardware specification.

IMPORTANT

Updating the service plan of your virtual machine has two constraints. You are not able to change the operating system and the VM needs to be in state ACTIVE or SHUTOFF.

CAUTION

When you update an existing service, and you have specified the additional parameter external-ip, previously, make sure that this additional parameter is specified properly as the default value is used, which means for external-ip the default value is false.
This could lead to a situation where the external-ip will be removed and when reassigning the external-ip could change the IP address and could impact existing firewall rules.

Updating a Virtual Machine via UI
When you are logged into the Stratos UI navigate to the service instance.


Select Edit on the context menu. This will open a dialog with two tabs. On the first tab you can select a new service plan.




On the next tab you can change the name of the service instance, but also update the service parameters such as external-ip and additional-storage, where you can assign or remove an external IP on your Linux or Windows virtual machine and/or provision additional storage on top of the chosen service plan.

When you add additional storage during update of a service instance the additional storage will be handled like stored added due to a service plan update, which means:

Windows virtual machines
For Windows virtual machines additional storage will be added to the D drive automatically, but you need to reboot the virtual machine, so that this change takes effect.

Linux virtual machines
For Linux virtual machines additional storage is not automatically mounted int the filesystem, but you can find documentation Add disk space on a Linux VMaaS VM.

When you click on finish the update will be triggered.

Updating a Virtual Machine via CLI
When your Cloud Foundry CLI is targeted at the organization/space where the service instance is located, you can get a list of all service instances in the space



cf services 
which will return a result like this



name     service           plan            bound apps   last operation     broker   upgrade available
jh       vmaas-jump-host   Linux SSH                    create succeeded   vmaas
vm-win   vmaas-windows     Large (W2K22)                update succeeded   vmaas 
To change the service plan of a service instance use



cf update-service <service-instance-name> -p <service-plan> 
for example



cf update-service vm-win -p "X-Large (W2K22)" 
to change the external IP in addition to the service plan use

Windows:



cf update-service <service-instance-name> -p <service-plan> -c "{\"external-ip\":<boolean>,\"additional-storage\":<number>}" 
Linux:



cf update-service <service-instance-name> -p <service-plan> -c '{"external-ip":<boolean>,"additional-storage":<number>}' 
for example



cf update-service vm-win -p "X-Large (W2K22)" -c "{\"external-ip\":true}" 
to just change the external IP without the service plan use

Windows:



cf update-service <service-instance-name> -c "{\"external-ip\":<boolean>}" 
Linux:



cf update-service <service-instance-name> -c '{"external-ip":<boolean>}' 
for example



cf update-service vm-win -c "{\"external-ip\":false}"

Binding and Unbinding a Virtual Machine with an Application
Created by 

 De Winter Commerina Aletta (BD/ISA-PRC2) on 2026, Feb 05  5 minute read Current Version V 1Page Info
When you run an application in Cloud Foundry that wants to connect to a service running on a virtual machine, you need to bind the application to the virtual machine that hosts that service.

When you bind an application to a virtual machine three things will be done:

The virtual machine will get a so-called floating IP, which is required to access the virtual machine from the outside.

The virtual machine gets a security group assigned that enables ingress from Cloud Foundry.

In Cloud Foundry an Application Security Group (ASG) will be created and assigned to the space where the application and the virtual machine are located. This application security group enables egress traffic for TCP and UDP on all ports to the floating IP of the virtual machine.

When you unbind the application from the virtual machine all these changes are reverted.

TIP

A tutorial video with practical examples for this content can also be available at this link.

When you have provisioned a virtual machine via UI or CLI, you need to get the Credentials you need to access the virtual machine. These credentials will be provided on two ways, either on the VMaaS Dashboard by following the link on the service instance in the Cloud Foundry Stratos UI, or on the Virtual Machine REST API. The Virtual Machine REST API provides an endpoint to get the details of a virtual machine:



GET /vms/{service-instance-id}



The response will contain the information about host name, fully qualified domain names (FQDN), IP addresses, username and initial password.



Before discussing on how to access a VMaaS virtual machine, it is necessary to clarify on which kind of virtual machine is accessible from where. Virtual Machine as a Service provides three services:

Virtual Machine Jump Host

Virtual Machine (Linux)

Virtual Machine (Windows)

A Jump Host virtual machine is intended as access point to the customer network, where all the virtual machines of the customer are located. The difference between a Jump Host virtual machine and a Linux / Windows Workload virtual machine is that a Jump Host virtual machine has an external IP by default but the required ingress security rules aren't automatically applied, therefore you have to apply it so the virtual machine is accessible from the outside. It is also possible to get an external IP for a workload virtual machine, and you can also configure the ingress so that it behaves similar like a Jump Host virtual machine, but is not recommended.

A Workload virtual machine will require an external IP to expose a service running on the virtual machine or when connecting to other services within the Bosch Private Cloud, but the ingress to a Workload virtual machine should be as restrictive as possible to minimize the exposure. You should access that virtual machines from the Jump Host virtual machine.

Access to a VMaaS Virtual Machine from the outside
Now that you have all necessary information to access the Jump Host virtual machine the next step is to decide on a way how to access.

TIP

It is recommended to use Privileged Session Management (PSM) for access VMaaS virtual machines. The benefits of using PSM are:
- PSM will automatically rotate passwords based on the Bosch central directives
- PSM maintains a 90-day audit log for access to all the virtual machines
- Access to the virtual machine is with your NT-ID credentials
- No additional Jump Host required for communication with the virtual machine

Depending on the foundation you have different options:

Internal Placement Zone (IPZ)
direct access from your Laptop in Bosch Corporate Network (BCN)

using RB-PAM to access your VMaaS VM

access using PSM to your Jumphost and then from Jump host to your Workload VM.

External Placement Zone (EPZ)
using RB-PAM to access your VMaaS VM

access using PSM to your Jump host



CAUTION

In the External Placement Zone (EPZ) no direct access from your Laptop in Bosch Corporate Network (BCN) via TCP/22 (SSH) and TCP/3389 (RDP) is allowed!

Access to VMaaS Jump Host
As mentioned earlier, a Jump Host does not come with the necessary security group rules applied by default for direct access. To enable these rules, follow these steps in your VMaaS web dashboard:

Navigate to the "Security Group Rules" tab.

Click the "+" icon.
Select the "Use a predefined security group" button.
Choose either "jumphost-ssh" for Linux Jump Hosts or "jumphost-rdp" for Windows Jump Hosts.




Once these rules are applied, you can connect directly to your Jump Host, or proceed to use PSM as explained in the next section for enhanced security.

Access to a VMaaS Virtual Machine using PSM
To connect to your Linux VMs using the Privileged Session Management (PSM) offered by RB-PAM, you will utilize PSMP (Privileged Session Management for SSH-Sessions).

The simplest way to connect is by copying the connection string directly from your VMaaS web dashboard. This string is pre-configured based on your current user ID, the server name, and RB-PAM default accounts.
Paste this string into your terminal, and when prompted, enter your NT-ID password to connect to your VM.







Alternatively, you can construct the connection string manually to connect with a user different from the default ones.

The example below illustrates the components of a PSMP connection string:


ssh	<NT-USER>	@	
rbadmin_app1

@	
c-bpc-0000001.vmaas.ipz001.internal.bosch.cloud

@	
rb-psmp.bosch.com



To connect to your Windows VMs using the PSM offered by RB-PAM, you will use **PSM4RDP**. The simplest method is to:

Download the RDP file directly from your **VMaaS web dashboard**.
Double-click the downloaded RDP file.
When prompted, enter your NT-ID password to establish the connection to your VM.








Alternatively, if you prefer using the RB-PAM web interface:

Open the RB-PAM web page (e.g., via the corporate portal).
Search for your VM name.
From the displayed account list, click the *"Connect"* button next to the desired account.
Provide a reason for your connection when prompted.
Open the generated RDP file to connect to your VM.

Created by 

 De Winter Commerina Aletta (BD/ISA-PRC2) on 2026, Feb 05  5 minute read Current Version V 1Page Info
Depending on the network location of your dependencies, you might need to explicitly create a rule in the E-IT and/or BPC firewalls to enable the communication from/to your VMs. In VMaaS, a virtual machine’s external communication is carried out through the so-called floating IPs, which can be assigned to or removed from your VMs at any time. Although this brings a good convenience, our service did not guarantee that a VM will always be assigned to the same floating IP. In addition, other customers could also get the floating IP that you used and released previously.

As a firewall rule relies on, in general, on an IP address, having a value that can change over time is not good as you might need to re-define firewall rule again in the future. With that in mind, we proposed a new marketplace service that allows to create a pool of floating IPs that can be used by your VMs only. That allows you to create the firewall rules for the corresponding floating IPs belonging to your pool a single time, avoiding extra rework.

One floating IP pool should be used for a set of virtual machines that require the same set of firewall rules (e.g. build workers), so if you have different kind of virtual machines it is recommended to have separate floating IP pools for those different kind of virtual machines. When creating/updating a virtual machine, where you specify a specific floating IP pool, an available floating IP from that floating IP pool is used.

The next sections explain how to create and delete such resource.

Create a new floating IP pool
The process to create a new pool is similar to that to create a VM, i.e., you can use both the Cloud Foundry’s Stratos UI or the CLI.

For the first, log into the platform and go to the Marketplace page. There, search for the "Floating IP Pool for your VMaaS VMs" service and click over it. You are going to be redirected to a page which is identical to the one displayed below.




Once you hit the '+' button, choose one organization and space, and move to the next screens. At the last one, you will be required to enter a name and the size of your new pool. The maximum is 20. In case you need more FIPs, please contact us through any one of our support channels. Within a couple of minutes, your pool must be already ready for use.

If you would rather use the CLI, use the command below as your starting point.



$ cf create-service vmaas-floating-ip-pool "Floating IP Pool" <my-pool-name> -c '{"pool-size": <pool-size>}'
NOTE

Bear in mind that the resulting service instance cannot be bound to any app. 


Display addresses belonging to the pool
To check the floating IP addresses that belong to your pool, use the CLI and execute the following command:



$ cf service <my-pool-name> --params 

This command returns a list of objects that represent your floating IPs, including their IP addresses, statuses, and the hostnames of the VMs that are eventually associated to them:



{
  "floating_ips": [
    {
      "assigned_to": "",

      "status": "PROVISIONED"
    }

In the example above, all 5 floating IPs are available to be assigned to any of your VMs.

Expanding or shrinking your pool
To update your existing pool to add additional FIPs or remove some of them, you can also use both the Stratos UI and CLI. For the first, locate your service instance and then click in the Edit button as depicted by the image below. Choose your new pool size, accordingly.




If you want to use the CLI, use the cf update-service command as shown in the following snippet: 



$ cf update-service <my-pool-name> -c '{"pool-size": <new-pool-size>}'

Please, be aware that, in case you want to shrink your pool, but it does not have free FIPs (i.e., floating IPs that are not assigned to any VM), we will return you an error, and no floating IP will be released.

Deleting your pool
If you do not need your pool anymore, delete it through the Stratos UI or the CLI. For the UI, click on the 'Delete' button as shown below.


For the CLI, run cf delete-service and provide your pool’s name:



$ cf delete-service my-pool 

This request fails if any of your FIPs is still associated to a VM, so assure that you unassign any floating IP in use beforehand.

Migration a floating IP to a floating IP pool
Sometimes you have provisioned a VMaaS VM, but not used a floating IP pool. When you need to delete and re-build the VMaaS VM, you would lose the floating IP. To prevent this, we introduced a new service parameter, that allows you to migrate the floating IP to an existing floating IP pool.

Windows:



cf update-service <service instance name> -c "{\"migrate-to-floating-ip-pool\": \"<floating IP pool name>\"}" 

Linux:



cf update-service <service instance name> -c '{"migrate-to-floating-ip-pool": "<floating IP pool name>"}' 

There are a few things that you should know before:

You can not combine the new service parameter with a service plan change.

Other service parameters will be ignored when using service parameter migrate-to-floating-ip-pool.

A floating IP pool with the name specified need to be present in the same space.

The floating IP pool must be successfully created.

If a prerequisite is not fulfilled the service parameter has no effect.

Cloud Foundry provides the ability to share a service instance among multiple spaces and across organizations via Cloud Foundry Command Line Interface (CF CLI).

Download: https://github.com/cloudfoundry/cli/releases

Service instance sharing
You can share VMaaS service instance from one space to another if you have the Space Developer role in both spaces. To share a service instance to another space, run the following CF CLI command: 



cf share-service SERVICE-INSTANCE -s OTHER-SPACE [-o OTHER-ORG]

To verify that your service instance is shared, run the following CF CLI command:
 



cf service SERVICE-INSTANCE

The output should contain the following information:



Showing sharing info:
   Shared with spaces:
   org           space           bindings
   [your-org]    [your-space]    0 

When to use Service instance sharing with VMaaS
Use Case
Service instance sharing with VMaaS VMs is intended for the use case that you operate a service on your VMaaS VM that you want to access from multiple applications running in Cloud Foundry in different spaces/organizations.

VMaaS Binding
Towards service instance binding in Cloud Foundry, where credentials are created and injected into the VCAP_SERVICES environment variable, the VMaaS service is using service instance binding to enable the communication between the application running in Cloud Foundry and the VMaaS VM in Openstack.

VMaaS VM
To enable the communication between an application in Cloud Foundry and the VMaaS VM in Openstack, there are two things required on the VMaaS VM:

A floating IP, so that the VMaaS VM is reachable from outside the VMaaS Openstack tenant. If the VMaaS VM has no floating IP assigned, a floating IP will be assigned; otherwise no action.

An Openstack security group rule that enables the ingress on the VMaaS VM. This Openstack security group (vmaas-cloudfoundry) will enable any port for protocols TCP and UDP from Cloud Foundry.

Cloud Foundry
In addition to the configuration on the VMaaS VM also in Cloud Foundry the egress to the VMaaS VM needs to be enabled. This is done via Application Security Groups (ASG):

An application security group for the VMaaS VM will be created (name: vmaas-<service-instance-id>) that allows any port for protocols TCP and UDP to the floating IP of the VMaaS VM.

This application security group will be bound to the space in which the application is located for which the binding is executed.



NOTE

In former days a restage was required so that the application security group became active, but this is no longer required and egress is enabled immediately.

Service instance sharing and VMaaS binding
Without service instance binding a VMaaS VM can only be bound to an application deployed in the same space and organization, where the VMaaS VM was provisioned. With Service instance sharing it is possible to bind an application in a different space/organization to a shared VMaaS VM service instance. This will bind the application security group to the space of the application as well.

VMaaS Getting a URL to the Remote Console
Created by 

 De Winter Commerina Aletta (BD/ISA-PRC2), last updated by Dietzsch Alexander (BD/ISA-PRC3) on 2026, May 28  2 minute read Current Version V 3Page Info
Debugging virtual machines (VMs) can be a hard task when you cannot establish a secure remote connection to the VM. This might happen for many reasons, including wrong settings, failures at initialization, or boot issues, for example. At such cases, you would need another way to connect to your machine and analyze your logs. To accomplish this goal, VMaaS team has made available two new REST APIs that can be used to obtain a URL pointing to a short-lived web remote console. With that link, you can use your favorite web browser to find the root cause of your issue and fix it without the need of requesting another virtual machine. In addition, this feature has also been integrated to our dashboard, allowing you to open a connection to your VM in seconds. The core of this feature relies on the following REST APIs:

POST /vms/{service-instance-id}/remote-console/{type}/{protocol}.

GET /vms/{service-instance-id}/remote-console/{request-id}.

As usual, in order to use them, you need to be authenticated. More information on how to obtain a valid token can be found at this guide.

Without further ado, let’s check how to use these two new APIs in the next sections.

Requesting a new web console URL
The first step to get your remote console URL is calling POST /vms/{service-instance-id}/remote-console/{type}/{protocol} with a type and a protocol. Those two parameters can assume the values as described below:

The protocol of remote console. The valid values are vnc, spice, rdp, serial, and mks.

The type of remote console. The valid values are novnc, rdp_html5, spice_html5, serial, and webmks.

NOTE

As of now, due to the current deployed Openstack version, the only valid values for the type and protocol are vnc and novnc, respectively.

Since VMaaS handles the requests asynchronously, this API is going to return a UUID code, which then can be used to poll for the URL. The format of the response return by this POST API is depicted below:



{
  "requestId":"a5ee099e-d05f-4b62-9490-c3dba873a52e"
} 

Getting the web console’s URL from the UUID
After receiving a UUID` from the POST call, you can make another request, GET /vms/{service-instance-id}/remote-console/{request-id}, to get the current status of the URL generation process. Using the same UUID of the previous section’s example, calling GET /vms/{service-instance-id}/remote-console/a5ee099e-d05f-4b62-9490-c3dba873a52 would return one of the following answers, depending on the current processing status.

If VMaaS is still processing the request internally, then the CREATING status is returned, indicating that you should wait before calling the same API again.



{
    "status": "CREATING"
} 

If VMaaS was able to create a URL, then it returns that URL together with CREATED status

NOTE

by default, the url is valid for 10 minutes. After that period, follow the same process to request a new one.



{
    "url": "https://osp.ipz001.internal.bosch.cloud:13080/vnc_auto.html?path=%3Ftoken%3D3b275b83-05d1-4685-8224-696261fe185f",
    "status": "CREATED"
} 

Otherwise, in case of internal failures, we return CREATE_FAILED. In that case, retry your calls or contact us through any of our support channels.



{
    "status": "CREATE_FAILED"
}

VMaaS Managing Custom Proxy Destinations
Created by 

 De Winter Commerina Aletta (BD/ISA-PRC2), last updated by Povoacao Kleber (BD/ISA-PRC3) on 2026, May 14  4 minute read Current Version V 4Page Info
For security reasons, virtual machines (VMs) cannot directly access the Internet in Bosch. In case this is indeed a requirement, teams are requested to configure the proxy settings of such VMs.

The virtual machines provisioned by VMaaS are already set up with the addresses pointing to the proxy for the Bosch Private Cloud (more on here).

However, if you need access to a domain or address which is not allowed by default in the current web proxy’s settings, then you are required to request an exemption. In order to make this process faster and easier, BPC currently provides an internal platform, Proxy as a Service, which automatically handles exemptions. As VMaaS customers' time matter a lot to us, we developed an integration to this service, allowing you to enable domains (a.k.a. proxy destinations) for your VM in seconds.

Proxy destinations can be specified as an FQDN, a wildcard FQDN, IP address or CIDR notation.

Addition, deletion or updating a URL on proxy service, can be executed through VMaaS Dashboard or sending requests via REST API



Dashboard







Three REST APIs are provided:

GET /vms/{vmaasInstanceId}/proxy-destinations

POST /vms/{vmaasInstanceId}/proxy-destinations

DELETE /vms/{vmaasInstanceId}/proxy-destinations/{proxyDestinationId}

As usual, in order to use them, the user needs to be authenticated. More information can be found at this guide.

NOTE

A pre-requirement for this feature is that the VM has already been assigned to a floating IP.

Get all enabled destinations for a virtual machine
To get all the domains that a VM has been allowed for, just submit a request like below. service-instance-id is the GUID associated with your VM (refer to this page for information on how to retrieve this value).



GET /vms/{service-instance-id}/proxy-destinations 

The block below depicts an example of response that you might get. It contains a list of all domains that are active. This API also supports pagination, which consists of splitting the entries into multiple pages to avoid long answers. Use the optional parameters page and results-per-page to choose which page and how many entries each one contains, respectively. By default, they are defined as 0 and 20.



{
    "content": [
        {
            "destination_id": "895e83d9-0da8-4d83-aa62-02c8cef999a4",
            "destination": "100.200.200.200",
            "status": "CREATED"
        },
        {
            "destination_id": "d46af984-463e-4282-a0a5-58c5b0510a96",
            "destination": "100.200.202.200",
            "status": "CREATED"
        },
        {
            "destination_id": "7779d4a5-b595-4f06-9281-460a76cdd5b1",
            "destination": "www.google.com",
            "status": "CREATED"
        },
        {
            "destination_id": "a0ede5ba-2e88-4864-ac1e-ae701bbdc72d",
            "destination": "100.200.255.240",
            "status": "CREATED"
        }
    ],
    "page": {
        "size": 20,
        "number": 0,
        "totalPages": 1,
        "totalElements": 4
    }
}



Each destination contains the following attributes:

destination_id: an optional attribute that identifies the domain inside the Proxy as a Service platform. It may be empty in case the destination is in creation process.

destination: the domain which is associated with that entity.

status: the current status of the entity. It can assume the following values:

CREATING: the entity is being processed by the backend. At this step, VMaaS does not know its destination_id yet.

CREATED: the entity has been successfully created and is active.

UPDATED: because of the way Proxy as a Service has been developed, a destination might be shared among many VMs. Therefore, in case you perform an operation (add or delete) on a shared domain and it succeeded, then its status is going to be set to UPDATED. This means that it is currently active.

DELETING: the destination is being deleted by the backend. In this case, the associated domain is owned only by your VM.

COLLAPSING: the destination is being disassociated from the VM. In this case, the destination is shared with other VMs. To assure atomic access, no other VMs can perform operations on this destination until your request has been fulfilled.

EXPANDING: the destination is being associated to the VM. In this case, the destination is shared with other VMs.

CREATE_FAILED, UPDATE_FAILED, and DELETE_FAILED correspond to the failure status associated with the use cases below.

Associate a domain to a virtual machine
To submit a new domain allow request, our POST API can be used. It expects a body object containing a single field, destination. It can be an FQDN, a wildcard FQDN, an IP address or CIDR notation (i.e., 100.200.0.0/16).



POST /vms/{service-instance-id}/proxy-destinations
{
  "destination":"www.google.com"
} 

A pre-requirement for this operation is that the VM has already been assigned to a floating IP. A floating IP is needed for Internet connectivity. If it is not the case, VMaaS returns a 400 code.

NOTE

As a destination might be shared with other VM(s), you might need to wait for any in-progress operations performed on that destination to finish, even if they were not submitted by you. If this happens, wait for some seconds before your retry. You will get a 400 error containing "Proxy destination <id> is still being processed (current status is <status>)."

The operation is executed asynchronously, so that the REST API will return with a status code 202 (ACCEPTED).

Disassociate domain from a virtual machine
If you no longer need your custom proxy domain, it is a good practice to remove it from your VM. Submit a DELETE request for that, as depicted below:



DELETE /vms/{service-instance-id}/proxy-destinations/{proxy_destination_id} 

It relies only on the destination’s proxy_destination_id, which can be fetched from the GET API. This API is also asynchronous, returning 202 (ACCEPTED) in case the parameters are valid, i.e., the VM and the destination both exist, and are associated with each other.

VMaaS Managing Ingress and Egress
Created by 

 De Winter Commerina Aletta (BD/ISA-PRC2), last updated by Dietzsch Alexander (BD/ISA-PRC3) on 2026, Aug 16  6 minute read Current Version V 16Page Info
When you have provisioned a virtual machine the virtual machine requires connectivity to other virtual machines or services.

Connectivity within the subnet (Cloud Foundry Organization) is possible between all virtual machines on all ports for TCP, UDP and ICMP.

While connectivity within the customer tenant is enabled by default, connectivity to the outside is restricted and needs to be managed. This connectivity is managed via so-called security groups on Openstack.

There we distinguish between:

Ingress

Egress

As known from public Clouds we enable egress, at least within Bosch Private Cloud, while we restrict ingress.

NOTE

Egress rules outside BPC are also supported, but, due to security constraints, we must add them on your behalf. Cut us a ticket if you need a non-default egress rule (e.g., to enable connectivity to a service in the Enterprise network). You can still delete your custom egress rules using our DELETE API by yourself.

Virtual Machine as a Service provides you with self-service so that you can manage the ingress and egress of your virtual machine with predefined security groups on your own.

Predefined Security Groups
Available predefined security groups
jumphost-rdp
Security Group to grant access to RDP (allow TCP ingress traffic on port 3389 from any IPv4 address. Allow ingress from PSM for RDP on TCP ports: 135, 139, 445, 49152-65535. Allow ingress from PSM for RDP on UDP ports: 135, 139).

jumphost-ssh
Security Group to grant access to SSH (allow TCP ingress traffic on port 22 from any IPv4 address).

vmaas-psmp-ssh
Security Group to grant access to Linux VM from PSMP (allow SSH ingress traffic from CPM and PSMP).

vmaas-psmp-rdp
Security Group to grant access to Windows VM from PSM (allow RDP ingress traffic from CPM and PSM).

vmaas-ms-defender
Security Group to grant access to proxy servers required for Microsoft Defender.

vmaas-tsm
Security Group to grant access to TSM Backup (allow TCP egress traffic on port 1500 to the TSM Backup Servers).

vmaas-social-coding
Security Group to grant access to Social Coding Bitbucket (allow TCP egress traffic on port 443 to the Social Coding Bitbucket).

vmaas-rb-artifactory (available in IPZ only)
Security Group to grant access to RB Artifactory in SL3 (allow TCP egress traffic on port 443 to the RB Artifactory - https://rb-artifactory.bosch.com).

vmaas-shared01-artifacts
Security Group to grant access to shared01 Artifactory Platform instance in SL4 (allow TCP egress traffic on port 443 to the shared01 Artifactory - https://shared01.artifacts.app.bosch.com).

There is a new Artifactory shared01.artifacts.app.bosch.com available in SL4 which will be the replacement for RB-Artifactory.

vmaas-fossid (available in IPZ only)
Security Group to grant access to FOSSID Service in SL3 (allow TCP egress traffic on port 443 to the FOSSID Service - https://rb-fossid.de.bosch.com).

Meanwhile, there is also a FOSSID available in SL2 at https://foss-scanner.bosch.tech. When you want to use this instance, no Openstack Security Group is required, but you need to create Proxy Whitelisting for foss-scanner.bosch.tech, so that you can reach it via Proxy. This Proxy Whitelisting you can create via VMaaS REST API or in the VMaaS Dashboard on tab Custom Proxy Destinations.
vmaas-oracle
Security Group to grant access to Oracle Database Service (allow TCP egress traffic on port 38000 to the Oracle Database Servers).

vmaas-mathworks (available in IPZ only)
Security Group to grant access to Mathworks License Server - rb-lic-mlm-eu.de.bosch.com.

vmaas-vulnerability-scanner
Security Group to grant access from the Vulnerability Scanner to the VMaaS VM.

vmaas-ibc-ssh
Security Group to grant access to Linux VM from SASE Gateways for IBC Clients (allow SSH ingress traffic).

vmaas-ibc-rdp
Security Group to grant access to Windows VM from SASE Gateways for IBC Clients (allow RDP ingress traffic).

vmaas-ibc-prometheus-grafana
Security Group to grant access to Prometheus/Grafana/AlertManager from SASE Gateways for IBC Clients

vmaas-icinga
Security Group to grant access from Icinga to monitor a VMaaS VM.

vmaas-bcr2
Security Group to grant access to Bosch Container Registry - bcr2.inside.bosch.cloud.

Get all the security groups of a Virtual Machine via REST API
The Virtual Machine REST API provides an endpoint to get all the security groups of a virtual machine. It also supports pagination (i.e., entries split into multiple pages), so that you do not get huge answers. We offer you two optional parameters, page and results-per-page, that can define how many entries your request will return. The first represents the index of the page, meanwhile the seconds stands for the maximum number of entries per page. By default, they are 0 and 20, respectively.



GET /vms/{service-instance-id}/security-groups 

This will return you a list like this:



{
    "content": [
        {
            "name": "vmaas-tsm",
            "status": "ASSIGNED"
        }
    ],
    "page": {
        "size": 20,
        "number": 0,
        "totalPages": 1,
        "totalElements": 1
    }
} 

There you have a name that you need, when you want to remove the security group from your virtual machine.

Assign a security group on a Virtual Machine via REST API
The Virtual Machine REST API provides also an endpoint to assign a security group on a virtual machine



POST /vms/{service-instance-id}/security-groups/{security-group-name} 

The operation is executed asynchronous, so that the REST API will return with a status code 202 (ACCEPTED).

Remove a security group from a Virtual Machine via REST API
The Virtual Machine REST API provides also an endpoint to remove a security group from a virtual machine



DELETE /vms/{service-instance-id}/security-groups/{security-group-name} 

The required security group name you can get from the GET REST API.

The operation is executed asynchronous, so that the REST API will return with a status code 202 (ACCEPTED).

Individual Security Group Rules
Virtual Machine as a Service provides you with self-service so that you can manage the ingress of your virtual machines on your own.

Get all the rules of a Virtual Machine via REST API
The Virtual Machine REST API provides an endpoint to get all the security group rules of a virtual machine. It also supports pagination (i.e., entries split into multiple pages), so that you do not get huge answers. We offer you two optional parameters, page and results-per-page, that can define how many entries your request will return. The first represents the index of the page, meanwhile the seconds stands for the maximum number of entries per page. By default, they are 0 and 20, respectively.



GET /vms/{service-instance-id}/security-group-rules 

This will return you a list like this:



{
    "content": [
        {
            "security_rule_id": "9b50ea7a-9335-471e-8a70-243a3517b3e2",
            "direction": "ingress",

            "port_range_max": 3389,

There you have a security_rule_id that you need, when you want to delete the security group rule. Besides that you get the direction (ingress, egress), the protocol (e.g. tcp, udp, icmp, ..), the port range, the remote IPs as CIDR (any is represented as 0.0.0.0/0) and a description.

Create an ingress rule for a Virtual Machine via REST API
The Virtual Machine REST API provides also an endpoint to create a security group rule for a virtual machine



POST /vms/{service-instance-id}/security-group-rules 

This REST API call requires a request body in JSON format:



{
  "direction": "ingress",
  "protocol": "tcp",
  "port_range_min": 443,
  "port_range_max": 443,
  "remote_ip_prefix": "0.0.0.0/0",
  "description": "Allow Ingress on TCP/443 from anywhere"
} 

Attributes direction and protocol are required, while all other attributes are optional, which means any on ports and remote IPs.

The operation is executed asynchronous, so that the REST API will return with a status code 202 (ACCEPTED).

WARNING

Define the CIDR of the Remote IP Prefix for all your ingress security group rules as small as possible and try to prevent using any to reduce the attack surface from the outside. There is also a firewall on Operating System level that will control ingress, but if that is open and the endpoint is not secured by authorization and authentication this could unwillingly expose your VM and your data.

Delete an ingress/custom egress rule of a Virtual Machine via REST API
The Virtual Machine REST API provides also an endpoint to delete a security group rule for a virtual machine



DELETE /vms/{service-instance-id}/security-group-rules/{security-group-rule} 

The required security group rule you can get from the GET REST API.

The operation is executed asynchronous, so that the REST API will return with a status code 202 (ACCEPTED).

Communication to other Virtual Machines
The communication to all other virtual machines within the same organization is possible via ICMP, TCP and UDP on all ports. Communication to virtual machines in other organizations is not allowed by default, but can be enabled, when the owner of that other virtual machine is allowing the ingress.

Communication to the Internet
Communication to the Internet from a virtual machine is enabled by default, but needs to be established via Proxy. In case the resource on the Internet is not whitelisted it could be necessary to whitelist the resource, before you can use it.

When you communicate from your VMaaS virtual machine to the Internet via Proxy, then your virtual machine appears with the public IP address of the Proxy on the Internet, which is either 194.39.218.0/23 (IPZ001/EPZ001/IPZ002/EPZ002) or 45.112.36.0/22 (IPZ003).

In case you are still using deprecated proxy 10.143.0.177/32 or 10.143.16.65/32, then your virtual machine appears with the public IP address of the Proxy on the Internet, which is either 139.15.8.8/29 (IPZ001/EPZ001) or 139.15.8.16/29 (IPZ002/EPZ002). These deprecated addresses are going to be phased out on Q3/2025

For more information on proxy endpoint and proxy public IP range, please refer to: Proxy

Communication to other services in Bosch Private Cloud
By default, all other services within Bosch Private Cloud should be reachable from a virtual machine.

Communication to Enterprise IT
Communication to the Enterprise IT is in general allowed to SL1, SL2 and SL4, but at the moment only enabled for a set of predefined endpoints (see Egress Security Rules). At the moment managing egress is not enabled for self-service due to security restrictions.
